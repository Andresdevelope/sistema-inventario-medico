SISTEMA DE INVENTARIO MÉDICO — DIAGRAMA ENTIDAD-RELACIÓN (ER)
Fecha: 26/02/2026 (actualizado)

Este diagrama conceptual refleja las entidades principales del dominio, sus atributos y relaciones. Está alineado con las migraciones actuales y la trazabilidad por lote.

RESUMEN DE ENTIDADES Y RELACIONES
- Un PRODUCTO puede tener muchos LOTES (INVENTARIO_LOTE).
- Un LOTE puede tener muchos MOVIMIENTOS (entradas, salidas, ajustes).
- Un USUARIO puede registrar muchos MOVIMIENTOS.
 - Un DESTINO normaliza salidas y puede tener muchos MOVIMIENTOS.
 - Un MOVIMIENTO puede estar “leído” por muchos USUARIOS (pivot de lecturas para notificaciones).
 - Un USUARIO puede tener muchos PERMISOS y un PERMISO puede pertenecer a muchos USUARIOS (N:N).

RELACIONES PRINCIPALES
- CATEGORIA tiene muchas SUBCATEGORIAS y PRODUCTOS.
- SUBCATEGORIA agrupa PRODUCTOS.
- PROVEEDOR provee PRODUCTOS (relación lógica/modelo; sin FK física activa en migración de `productos`).
- PRODUCTO se divide en LOTES y participa en MOVIMIENTOS.
- LOTE se afecta por MOVIMIENTOS.
- USUARIO registra MOVIMIENTOS, genera REPORTES y realiza acciones en BITÁCORA.
 - DESTINO agrupa salidas (egresos) por área/unidad.
 - MOVIMIENTO <-> USUARIO (N:N) a través de movimiento_user_reads para marcar notificaciones leídas.
 - MOVIMIENTO (egreso) lleva una MODALIDAD: distribución (Central → Destinos) o consumo (entrega real).
 - USUARIO <-> PERMISO (N:N) a través de permission_user para autorización granular por módulo/acción.

ATRIBUTOS CLAVE POR ENTIDAD
- CATEGORIA: id, nombre
- SUBCATEGORIA: id, nombre
- PROVEEDOR: id, nombre, contacto, teléfono, dirección, email
- PRODUCTO: id, nombre, código, descripción, categoría, subcategoría, presentación, unidad_medida, tipo_producto (medicamento|insumo), categoria_inventario, stock, stock_mínimo, proveedor_id, created_by, updated_by, fechas
- INVENTARIO_LOTE: id, lote, cantidad, fecha_vencimiento, um_operativa, contenido_por_blister, estado
- MOVIMIENTO: id, tipo (ingreso|egreso|ajuste_pos|ajuste_neg), modalidad (distribucion|consumo en egreso), cantidad, fecha, área/salida, destino_id, origen/entrada, motivo, observaciones, tipo_identificacion, sexo
- USUARIO: id, nombre, email, rol, login_attempts, locked_until, notif_mov_last_seen_id
- PERMISO: id, slug, nombre, grupo
- REPORTE: id, nombre, tipo, parámetros/filtros (json; columna física actual: `para  metros`)
- BITÁCORA: id, acción, fecha_hora
 - DESTINO: id, codigo, nombre, activo, tipo
 - MOVIMIENTO_USER_READS (pivot): movimiento_id, user_id, read_at
 - PERMISSION_USER (pivot): permission_id, user_id, created_at, updated_at

CARDINALIDADES
- Un Producto puede tener 0..N Lotes.
- Un Movimiento afecta 1 Producto y 0..1 Lote (inventario_id nullable; se recomienda 1 lote en egresos/ajustes para trazabilidad).
- Un Usuario registra 0..N Movimientos, genera 0..N Reportes y tiene 0..N registros en Bitácora.
- Un Usuario tiene 0..N permisos granulares (si es operador).
- Un Proveedor suministra 0..N Productos.
 - Un Destino recibe 0..N egresos (distribución y consumo); la modalidad se define por movimiento.


NOTAS
- El ER es conceptual: ayuda a entender el negocio y las relaciones.
- Se recomienda mantener la relación Movimiento → Lote obligatoria para maximizar la trazabilidad.
- Si se maneja vencimiento por lote, usar fecha_vencimiento para priorizar salidas (FEFO), con FIFO por `created_at` en empates (tal como se implementa en `InventarioService::getInventariosFefoFifo`).
 - En consumo, se registran datos mínimos del beneficiario (tipo_identificación y sexo); no se guardan datos personales.
- No se permite consumo originado en Central; Odontología sólo egresa insumos (validado por `producto.tipo_producto`).
- El sistema implementa seguridad reforzada: autenticación obligatoria, autorización por rol, protección CSRF en formularios, sanitización de datos de entrada y control de intentos de acceso.
 - Seguridad reforzada adicional: rate limiting en login y recuperación, reCAPTCHA v2 opcional en login/registro, bloqueo por intentos fallidos con desbloqueo por admin.
- Los movimientos y acciones relevantes quedan registrados en bitácora para auditoría.

ACTUALIZACIÓN 08/02/2026
- Se incorporó en la capa de presentación el helper `mov_formatear_destino()` para normalizar cadenas complejas de destino antes de mostrarlas. Esto no modifica el ER pero refuerza el concepto de DESTINO como entidad única y evita que alias manuales afecten la trazabilidad documentada.
- La vista de movimientos ahora define internamente `tipo` y `modalidad` con valores por defecto (cuando no son suministrados por el controlador), asegurando que las relaciones MOVIMIENTO → DESTINO/USUARIO se mantengan coherentes en todo el flujo descrito por este diagrama conceptual.

ACTUALIZACIÓN 26/02/2026
- Se incorpora en el ER el atributo `users.notif_mov_last_seen_id` para seguimiento de notificaciones de movimientos.
- Se aclara que `productos.proveedor_id`, `productos.created_by` y `productos.updated_by` existen a nivel de atributo y modelo, pero actualmente no tienen FK física declarada en migraciones.
- Se ajusta cardinalidad conceptual de MOVIMIENTO → INVENTARIO_LOTE a 0..1 para reflejar nulabilidad real de `inventario_id`.

ACTUALIZACIÓN 08/03/2026
- Se incorporan las entidades de autorización granular: `PERMISO` y pivote `PERMISSION_USER`.
- Se formaliza en el modelo conceptual que:
	- `admin` mantiene acceso total por política del sistema.
	- `operador` accede por permisos de checklist (categorías, medicamentos, inventario, movimientos, reportes).
- Se documenta la protección de superadmin (primer usuario del sistema) para operaciones críticas de gestión de usuarios.
- Se añade validación reforzada en categorías/subcategorías con sanitización y filtros anti-entrada sospechosa (backend + frontend).
