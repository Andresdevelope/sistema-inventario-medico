SISTEMA DE INVENTARIO MÉDICO — FLUJO FUNCIONAL (INTEGRAL)
Fecha: 16/03/2026

Objetivo
- Documentar el flujo completo del sistema (autenticación, autorización, módulos operativos, auditoría y reportes) en un formato textual neutral, reutilizable y adaptable para cualquier herramienta de representación visual.

============================================================

2) FLUJOS ESPECÍFICOS COMPLEMENTARIOS (TEXTO ESTRUCTURADO)
============================================================

2.1 Flujo de recuperación de contraseña

Nodos (ID -> descripción)
- RA -> Usuario va a Recover.
- RB -> Ingresa correo.
- RC -> Validación backend + throttle + reCAPTCHA opcional.
- RD -> Decisión: ¿correo válido?
- RE -> Respuesta uniforme + emisión de flow_token temporal.
- RF -> Preguntas de seguridad (color, animal, padre según flujo).
- RG -> Decisión: ¿respuestas válidas?
- RH -> Denegar + mensaje en español.
- RI -> Envío de token de correo (6 dígitos) y visualización de hint de correo enmascarado.
- RJ -> Cuenta regresiva del token (frontend) + control backend por expiración.
- RK -> Usuario ingresa token de correo.
- RL -> Decisión: ¿token válido (hash + intentos)?
- RM -> Nueva contraseña.
- RN -> Validaciones robustas.
- RO -> Decisión: ¿cumple política?
- RP -> Mensaje en español.
- RQ -> Guardar contraseña + éxito.

Transiciones
- RA -> RB | usuario inicia recuperación.
- RB -> RC | correo enviado a validación.
- RC -> RD | backend procesa correo.
- RD -> RE | respuesta uniforme para evitar enumeración.
- RE -> RF | flow_token emitido y proceso activo.
- RF -> RG | respuestas enviadas.
- RG -> RH | respuestas inválidas.
- RG -> RI | respuestas válidas.
- RI -> RJ | token enviado por correo y desafío activo.
- RJ -> RK | usuario ingresa token de 6 dígitos.
- RK -> RL | backend valida hash, expiración e intentos.
- RL -> RH | token inválido/expirado o intentos agotados.
- RL -> RM | token válido.
- RM -> RN | propuesta de nueva contraseña.
- RN -> RO | evaluación de política.
- RO -> RP | no cumple política.
- RO -> RQ | cumple política.

2.2 Flujo de asignación de permisos a operador

Nodos (ID -> descripción)
- PA -> Admin abre módulo Usuarios.
- PB -> Abre modal de permisos.
- PC -> GET permisos actuales del operador.
- PD -> Checklist por grupos.
- PE -> Seleccionar/deseleccionar permisos.
- PF -> Confirmar contraseña admin.
- PG -> PUT actualizar permisos.
- PH -> Decisión: ¿validación OK?
- PI -> Error en español.
- PJ -> Sync permission_user + bitácora.

Transiciones
- PA -> PB | iniciar gestión de permisos.
- PB -> PC | cargar permisos actuales.
- PC -> PD | mostrar checklist.
- PD -> PE | edición de selección.
- PE -> PF | confirmar cambios sensibles.
- PF -> PG | envío de actualización.
- PG -> PH | backend valida operación.
- PH -> PI | validación con error.
- PH -> PJ | validación exitosa.

============================================================
3) NOTAS OPERATIVAS
============================================================

- Para solicitudes no-GET/AJAX denegadas por permisos, se responde 401/403 en JSON para evitar redirecciones con método HTTP incorrecto.
- Admin mantiene acceso funcional total; operador accede según checklist granular.
- Superadmin (usuario inicial) está protegido en operaciones críticas de gestión de usuarios.
- Validaciones clave están duplicadas en frontend y backend (defensa en profundidad).

============================================================
4) VERSIÓN NARRATIVA RESUMIDA
============================================================

4.1 Flujo general del sistema

1) Inicio
    -> Usuario abre la aplicación.
    -> El sistema verifica si hay sesión activa.

2) Si NO hay sesión
    -> Usuario entra por Login/Registro/Recuperación.
    -> Frontend valida campos.
    -> Backend valida + aplica seguridad (CSRF, throttle, reCAPTCHA opcional).
    -> Si falla: mensaje en español (y bloqueo por intentos cuando aplica).
    -> Si pasa: redirección a Dashboard.

3) Si SÍ hay sesión
    -> Va directo a Dashboard.

4) Control de acceso
    -> Si rol admin: acceso funcional total a módulos.
    -> Si rol operador: acceso según permisos granulares del checklist.

5) Navegación por módulos
    -> Perfil: validación de seguridad y cambio de contraseña.
    -> Usuarios (solo admin):
        - crear/editar/eliminar/desbloquear/asignar permisos.
        - operaciones sensibles exigen contraseña admin.
        - se aplican reglas de superadmin y límite de admins.
        - todo queda en bitácora.
    -> Categorías/Subcategorías:
        - validación frontend (max 35 + anti-basura).
        - validación backend equivalente + unicidad.
        - guardar y registrar bitácora.
    -> Productos:
        - validaciones de formato, negocio y fechas.
        - persistencia y bitácora.
    -> Inventario:
        - consulta por filtros, KPIs, vencimientos.
        - bitácora de acceso.
    -> Movimientos:
        - autorización por tipo (entrada/distribución/consumo/ajustes).
        - lógica de servicio de inventario (FEFO/FIFO y reglas de destino).
        - éxito/error con mensajes en español y bitácora.
    -> Reportes:
        - permisos por tipo de reporte.
        - validación de rangos/filtros.
        - generación de vistas/exportes + bitácora.
    -> Bitácora:
        - consulta de acciones críticas.
    -> Notificaciones:
        - lectura de movimientos y marca de leídos.

6) Recuperación de contraseña (resumen)
    -> validar correo (respuesta uniforme + flow_token)
    -> validar preguntas de seguridad (2 + 1 opcional)
    -> enviar token de correo (6 dígitos)
    -> validar token (hash, expiración, intentos, cooldown de reenvío)
    -> validar nueva contraseña
    -> guardar.

7) Cierre de sesión
    -> registrar logout en bitácora -> terminar sesión.

4.2 Flujo detallado de categorías/subcategorías

1) Usuario abre formulario crear/editar.
2) Frontend sanitiza (trim + colapso de espacios).
3) Frontend valida:
    - longitud <= 35
    - formato permitido
    - no patrones sospechosos (111111, aaaaaa, texto basura)
4) Si falla: bloquea envío y muestra mensaje en español.
5) Si pasa: envía al backend.
6) Backend repite sanitización y validación robusta + unicidad.
7) Si falla: responde error en español.
8) Si pasa: guarda cambios, registra bitácora y refresca UI.
