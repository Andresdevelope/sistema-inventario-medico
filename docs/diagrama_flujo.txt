1) FLUJO INTEGRAL DEL SISTEMA (MERMAID)
============================================================

flowchart TD

     B -->|No| C[Auth: Login / Registro / Recuperación]

     C3 -->|OK| D[Entrar a Dashboard]

     B -->|Sí| D

     D --> E{Rol y permisos}

     I --> I6[Movimientos]
     I --> I7[Reportes]

     I --> I9[Notificaciones]

     U2 --> U3{Regla superadmin / límite admins}
     U3 -->|No cumple| U4[Denegar + bitácora]

     U1 -->|No| U5

     I3 --> K0[Middleware permission:categorias.*]

     K1 --> K2[Validación backend + sanitización + unicidad]
     K2 --> K3{Válido?}
     K3 -->|No| K4[Error en español]
     K3 -->|Sí| K5[Guardar categoría/subcategoría]

     I4 --> P0[Middleware permission:medicamentos.*]
     P0 --> P1[Validación frontend]
     P1 --> P2[Validación backend\nformato, reglas de negocio, fechas]
     P2 --> P3{Válido?}
     P3 -->|No| P4[Error en español]
     P3 -->|Sí| P5[Persistir producto]
     P5 --> P6[Bitácora]

     M2 --> M7
     M3 --> M7
     M4 --> M7
     M5 --> M7

2) FLUJOS ESPECÍFICOS COMPLEMENTARIOS (MERMAID)
============================================================

2.1 Flujo de recuperación de contraseña

flowchart TD
     RA[Usuario va a Recover] --> RB[Ingresa correo]
     RB --> RC[Validación backend + throttle + reCAPTCHA opcional]
     RC --> RD{Correo válido?}
     RD -->|No| RE[Mensaje en español]
     RD -->|Sí| RF[Preguntas de seguridad\n(color, animal, padre según flujo)]
     RF --> RG{Respuestas válidas?}
     RG -->|No| RH[Denegar + mensaje en español]
     RG -->|Sí| RI[Nueva contraseña]
     RI --> RJ[Validaciones robustas]
     RJ --> RK{Cumple política?}
     RK -->|No| RL[Mensaje en español]
     RK -->|Sí| RM[Guardar contraseña + éxito]

2.2 Flujo de asignación de permisos a operador

flowchart TD
     PA[Admin abre módulo Usuarios] --> PB[Abre modal de permisos]
     PB --> PC[GET permisos actuales del operador]
     PC --> PD[Checklist por grupos]
     PD --> PE[Seleccionar/deseleccionar permisos]
     PE --> PF[Confirmar contraseña admin]
     PF --> PG[PUT actualizar permisos]
     PG --> PH{Validación OK?}
     PH -->|No| PI[Error en español]
     PH -->|Sí| PJ[Sync permission_user + bitácora]

============================================================
3) NOTAS OPERATIVAS
============================================================

- Para solicitudes no-GET/AJAX denegadas por permisos, se responde 401/403 en JSON para evitar redirecciones con método HTTP incorrecto.
- Admin mantiene acceso funcional total; operador accede según checklist granular.
- Superadmin (usuario inicial) está protegido en operaciones críticas de gestión de usuarios.
- Validaciones clave están duplicadas en frontend y backend (defensa en profundidad).

============================================================
4) VERSIÓN EN TEXTO PLANO (SIN MERMAID)
============================================================

4.1 Flujo general del sistema

1) Inicio
    -> Usuario abre la aplicación.
    -> El sistema verifica si hay sesión activa.

2) Si NO hay sesión
    -> Usuario entra por Login/Registro/Recuperación.
    -> Frontend valida campos.
    -> Backend valida + aplica seguridad (CSRF, throttle, reCAPTCHA opcional).
    -> Si falla: mensaje en español (y bloqueo por intentos cuando aplica).
    -> Si pasa: redirección a Dashboard.

3) Si SÍ hay sesión
    -> Va directo a Dashboard.

4) Control de acceso
    -> Si rol admin: acceso funcional total a módulos.
    -> Si rol operador: acceso según permisos granulares del checklist.

5) Navegación por módulos
    -> Perfil: validación de seguridad y cambio de contraseña.
    -> Usuarios (solo admin):
        - crear/editar/eliminar/desbloquear/asignar permisos.
        - operaciones sensibles exigen contraseña admin.
        - se aplican reglas de superadmin y límite de admins.
        - todo queda en bitácora.
    -> Categorías/Subcategorías:
        - validación frontend (max 35 + anti-basura).
        - validación backend equivalente + unicidad.
        - guardar y registrar bitácora.
    -> Productos:
        - validaciones de formato, negocio y fechas.
        - persistencia y bitácora.
    -> Inventario:
        - consulta por filtros, KPIs, vencimientos.
        - bitácora de acceso.
    -> Movimientos:
        - autorización por tipo (entrada/distribución/consumo/ajustes).
        - lógica de servicio de inventario (FEFO/FIFO y reglas de destino).
        - éxito/error con mensajes en español y bitácora.
    -> Reportes:
        - permisos por tipo de reporte.
        - validación de rangos/filtros.
        - generación de vistas/exportes + bitácora.
    -> Bitácora:
        - consulta de acciones críticas.
    -> Notificaciones:
        - lectura de movimientos y marca de leídos.

6) Recuperación de contraseña (resumen)
    -> validar correo -> validar respuestas de seguridad -> validar nueva contraseña -> guardar.

7) Cierre de sesión
    -> registrar logout en bitácora -> terminar sesión.

4.2 Flujo detallado de categorías/subcategorías

1) Usuario abre formulario crear/editar.
2) Frontend sanitiza (trim + colapso de espacios).
3) Frontend valida:
    - longitud <= 35
    - formato permitido
    - no patrones sospechosos (111111, aaaaaa, texto basura)
4) Si falla: bloquea envío y muestra mensaje en español.
5) Si pasa: envía al backend.
6) Backend repite sanitización y validación robusta + unicidad.
7) Si falla: responde error en español.
8) Si pasa: guarda cambios, registra bitácora y refresca UI.
