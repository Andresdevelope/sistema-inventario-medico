Introducción
La intención de este documento es definir los requerimientos funcionales y no funcionales del Sistema de Gestión de Insumos Médicos de la UPTAG, que permitirá administrar de manera eficiente los insumos médicos utilizados en los servicios internos de la universidad.
Propósito
El propósito de este documento es especificar los requerimientos funcionales y no funcionales del Sistema de Gestión de Insumos Médicos de la UPTAG, cuyo objetivo es administrar de manera eficiente los insumos médicos utilizados en los servicios internos de la universidad.
Alcance
El sistema permitirá:
Registrar y gestionar usuarios con diferentes roles (Administrador, Operador, Auditor).
Administrar categorías, subcategorías y productos médicos.
Controlar inventario, movimientos de entradas, distribución, consumos, ajustes + y ajustes -.
Generar reportes y análisis de consumo.
Emitir alertas y notificaciones por stock crítico.
El sistema será utilizado exclusivamente por el personal autorizado de los Servicios Médicos de la UPTAG.

Restricciones
El desarrollo del sistema de inventario médico estará condicionado por las siguientes limitaciones, que deben ser consideradas en todas las fases del proyecto:

- Lenguaje y framework: El sistema se implementará utilizando el lenguaje PHP y el framework Laravel, conforme a los lineamientos establecidos por la asignatura y las recomendaciones de la comunidad de desarrollo.

- Gestor de base de datos: Se empleará MySQL como sistema gestor de base de datos, por lo que la estructura de datos y las consultas deberán ser compatibles con este motor.

- Sistema operativo: El entorno de desarrollo y despliegue principal será Windows, aunque se procurará mantener la compatibilidad con sistemas Linux para facilitar futuras migraciones o pruebas.

- Normas de seguridad: El sistema deberá incorporar mecanismos de control de acceso, validación de datos y protección frente a vulnerabilidades comunes, tales como inyección SQL, XSS y CSRF, siguiendo las buenas prácticas de desarrollo seguro.

- Restricciones de hardware: El sistema debe ser capaz de operar en servidores con recursos limitados, optimizando el uso de CPU y memoria, y evitando procesos que puedan afectar el rendimiento general.

- Metodología de desarrollo: Se recomienda la adopción de metodologías ágiles, como Scrum o Kanban, para facilitar la gestión de cambios, la colaboración en equipo y la entrega continua de funcionalidades.

- Interfaz de usuario: La aplicación deberá ser accesible desde navegadores web modernos y adaptarse a diferentes resoluciones de pantalla, garantizando la usabilidad y accesibilidad para todos los usuarios.

Estas restricciones buscan asegurar la viabilidad técnica, la seguridad y la calidad del sistema, así como su alineación con los objetivos académicos del proyecto.

Suposiciones y dependencias
El sistema de inventario médico desarrollado en Laravel presenta las siguientes suposiciones y dependencias, derivadas de su arquitectura y entorno de implementación:

- Los usuarios acceden al sistema mediante navegadores web compatibles, en equipos con conectividad estable a la red local o internet.
- La autenticación y gestión de permisos se realiza a través de los mecanismos nativos de Laravel, utilizando roles y validaciones definidos en la plataforma.
- El sistema opera sobre un servidor con sistema operativo Windows, con soporte para PHP y MySQL, conforme a la configuración actual del entorno de desarrollo.
- La persistencia de datos depende del correcto funcionamiento del motor de base de datos MySQL y de la integridad de las migraciones y modelos definidos en el proyecto.
- El sistema utiliza dependencias gestionadas por Composer, incluyendo el framework Laravel y librerías asociadas, por lo que requiere que dichas dependencias estén instaladas y actualizadas.
- La infraestructura tecnológica de la institución (hardware, red, políticas de seguridad) constituye un factor externo que puede influir en la disponibilidad y rendimiento del sistema.
- La veracidad y consistencia de la información almacenada depende de los datos proporcionados por los usuarios y de los controles de validación implementados en los formularios y controladores.

Estas suposiciones y dependencias reflejan el estado actual del sistema y su contexto de operación, proporcionando un marco realista para la evaluación y documentación del proyecto.

Requisitos específicos
RF 01 – Autenticación de usuarios

Autenticación de usuario
Entradas:
- Email (string, requerido, formato válido, dominio institucional preferente)
- Contraseña (string, requerido, longitud >= 16, validación de complejidad)
- reCAPTCHA Token (string, opcional según configuración)
- Respuestas a preguntas de seguridad (strings, requeridas para recuperación)
Prioridad del requisito
Alta / Esencial
1. Usuario ingresa email y contraseña (+ reCAPTCHA si está habilitado).
2. El sistema valida reCAPTCHA (si aplica). Si falla, rechaza el intento.
3. Verifica si la cuenta está bloqueada (locked_until > ahora). Si bloqueada, muestra mensaje y no permite acceso.
4. Valida credenciales: si correctas, limpia contadores de fallos, crea sesión, registra inicio en bitácora y redirige al dashboard.
5. Si credenciales incorrectas, incrementa contador de fallos. Si alcanza el umbral, bloquea la cuenta por tiempo definido, notifica por correo y registra en bitácora.
6. Para recuperación, usuario solicita restablecimiento: el sistema envía enlace al correo o solicita respuestas de seguridad. Si validado, permite cambio de contraseña.
7. Para acciones críticas (gestión de usuarios, permisos), el sistema puede requerir doble validación (reingreso de contraseña o código temporal).
8. El sistema registra todos los eventos relevantes: inicio de sesión, bloqueos, recuperaciones, cambios de contraseña, intentos fallidos, cambios de permisos.
• La recuperación de contraseña debe ofrecer dos modalidades: envío de enlace seguro al correo institucional y validación mediante preguntas de seguridad predefinidas por el usuario.
• El sistema debe permitir la reactivación de cuentas bloqueadas solo por el Administrador o tras el vencimiento del periodo de bloqueo.
• Si el servidor de reCAPTCHA no responde, aplica política de fallback (denegar o permitir según configuración) y registra incidente.
• Si el servicio de correo falla al notificar bloqueo o recuperación, registra error en logs y bitácora.
• Si el usuario olvida respuestas de seguridad, puede solicitar asistencia al administrador (registro en bitácora).
• Los roles y permisos deben ser gestionados de forma granular, permitiendo asignar permisos específicos a cada usuario o grupo, y protegiendo las acciones críticas mediante doble validación si es necesario.
RF 01.1 – Gestión de usuarios
• Intentos múltiples: bloqueo temporal, mensajes claros sin revelar si el correo existe.
• Protección de información: no mostrar detalles que permitan enumerar usuarios.
• Registrar todos los eventos críticos en bitácora y logs.
• Errores en doble validación o recuperación generan alertas internas para revisión administrativa.
Gestión de usuarios
RF 01.1
• Código HTTP 200 + sesión activa y payload con datos mínimos del usuario (id, nombre, rol).
• Errores: 401 (credenciales), 423 (locked), 400 (bad request/reCAPTCHA), 403 (doble validación fallida).
• Mensajes de recuperación y bloqueo enviados por correo y registrados en bitácora.
Tipo
Requisito

• bitacora: id, user_id, action, module, ip, metadata, created_at

Descripción del requisito: El sistema debe registrar automáticamente todas las acciones relevantes realizadas por los usuarios: creación, edición, eliminación, movimientos de insumos, inicio de sesión. La bitácora debe incluir fecha, hora, usuario, módulo y acción. Solo el Administrador puede visualizarla.

• La bitácora debe registrar de forma automática y detallada todos los eventos críticos del sistema: autenticaciones, bloqueos, recuperaciones, cambios de permisos, movimientos de inventario, generación de reportes, y cualquier acción administrativa relevante.
• Cada registro debe incluir: fecha y hora exacta, usuario responsable (o anónimo si aplica), módulo afectado, tipo de acción, dirección IP, y metadatos adicionales (por ejemplo, cambios realizados, valores anteriores y nuevos).
• El sistema debe permitir la consulta de la bitácora mediante filtros avanzados: por usuario, módulo, tipo de acción, rango de fechas y nivel de criticidad.
• La visualización de la bitácora está restringida a Administradores y Superadministradores, con opción de exportar registros en formato PDF o Excel para auditoría.
• Debe existir un mecanismo de retención y depuración periódica de registros, configurable por el Administrador.
• El acceso y consulta de la bitácora también debe quedar registrado para garantizar la trazabilidad completa.

Descripción del requisito: El sistema debe permitir crear, editar y eliminar categorías de insumos médicos. Cada categoría puede tener subcategorías asociadas según tipo de presentación. Esta funcionalidad está disponible para Administrador y Operador.
Actualización y ampliación:
• El sistema debe garantizar la unicidad de nombres de categoría y subcategoría dentro de la misma jerarquía, evitando duplicados y permitiendo la edición segura.

• La interfaz debe permitir la visualización jerárquica de categorías y subcategorías, con filtros y búsqueda avanzada.
• El sistema debe validar la integridad referencial y mostrar mensajes claros ante errores o restricciones.
• Debe existir un mecanismo para reactivar categorías o subcategorías previamente desactivadas, conservando su historial.

• La interfaz debe mostrar el stock actual, el estado, los lotes activos y próximos a vencer, y permitir búsquedas avanzadas por nombre, lote, proveedor o estado.

## RF-01 — Autenticación de usuarios (Rediseñado)

### Entradas
- **username**: string, requerido, único, sensible a mayúsculas/minúsculas.
- **password**: string, requerido, longitud mínima 16 caracteres, validación de complejidad.
- **recaptcha_token**: string, requerido solo si reCAPTCHA está habilitado.

### Flujo principal
1. El usuario envía `username`, `password` y, si aplica, `recaptcha_token`.
2. El sistema valida el token reCAPTCHA (si está habilitado).  
	 - Si falla, responde HTTP 400 con mensaje "Verificación reCAPTCHA fallida".
3. Verifica si la cuenta está bloqueada (`locked_until > ahora`).  
	 - Si está bloqueada, responde HTTP 423 con mensaje genérico de bloqueo.
4. Valida credenciales:
	 - Si son correctas:
		 - Limpia contadores de fallos.
		 - Crea sesión.
		 - Registra inicio en bitácora.
		 - Responde HTTP 200 con payload mínimo del usuario (id, nombre, rol).
	 - Si son incorrectas:
		 - Incrementa contador de fallos.
		 - Si alcanza el umbral (ej. 5 intentos en 15 min):
			 - Bloquea la cuenta (`locked_until = ahora + 15min`).
			 - Notifica por correo (si corresponde).
			 - Registra evento en bitácora.
			 - Responde HTTP 423 con mensaje de bloqueo.
		 - Si no alcanza el umbral, responde HTTP 401 con mensaje genérico.

### Flujo alternativo
- Si el servidor reCAPTCHA no responde:
	- Aplica política de fallback (denegar o permitir según configuración).
	- Registra incidente en bitácora.
- Si falla el envío de correo de notificación:
	- Registra error en logs y bitácora con nivel WARNING.
- Si ocurre un error inesperado:
	- Responde HTTP 500 y registra en logs/bitácora.

### Manejo de errores
- Mensajes genéricos, nunca indicar si el usuario existe o no.
- Bloqueo temporal tras múltiples intentos fallidos.
- Registro de eventos críticos en bitácora y logs.
- Protección contra enumeración de usuarios.

### Salidas
- **Éxito:** HTTP 200, sesión activa, payload: `{ id, nombre, rol }`.
- **Error de credenciales:** HTTP 401, mensaje genérico.
- **Cuenta bloqueada:** HTTP 423, mensaje genérico.
- **Error reCAPTCHA:** HTTP 400, mensaje específico.
- **Error interno:** HTTP 500, mensaje genérico.

### Campos mínimos en la base de datos
**Tabla `users`:**
- id (PK)
- username (string, único, case-sensitive)
- password (hash)
- role (string)
- active (boolean)
- locked_until (datetime, nullable)
- failed_attempts (int, opcional)
- created_at (datetime)
- updated_at (datetime)

**Tabla `bitacora`:**
- id (PK)
- user_id (nullable, FK a users)
- action (string)
- module (string)
- ip (string)
- metadata (json)
- created_at (datetime)

### Parámetros y constantes
- `LOCK_DURATION_MINUTES = 15`
- `FAILED_ATTEMPTS_THRESHOLD = 5`
- `FAILED_ATTEMPTS_WINDOW_MINUTES = 15`

### Criterios de aceptación
- El sistema responde HTTP 200 y retorna datos mínimos del usuario al autenticarse correctamente.
- El sistema bloquea la cuenta tras 5 intentos fallidos en 15 minutos y responde HTTP 423.
- El sistema nunca revela si el usuario existe o no en los mensajes de error.
- Todos los eventos críticos (bloqueos, errores, accesos) se registran en la bitácora.
- Si reCAPTCHA está habilitado, la autenticación solo es posible con un token válido.

 Hasta 50 transacciones por hora en módulos críticos como movimientos de insumos.
 Exportación de reportes (PDF) en menos de 5 segundos para hasta 100 registros.
 Generación de alertas por stock mínimo en menos de 1 segundo tras el movimiento.
 Disponibilidad del servidor local estimada en 99% durante horario operativo.

Seguridad
Encriptación de contraseñas mediante bcrypt.
Validación de formularios en frontend y backend.
Protección contra SQL Injection, CSRF y XSS.
Middleware de roles y permisos para controlar el acceso a módulos.
Registro de acciones en bitácora de auditoría: inicio de sesión, creación, edición, eliminación, movimientos.
Restricción de acceso a rutas sensibles según rol.
Comprobación de integridad en movimientos y exportaciones mediante validaciones internas.

Fiabilidad
El sistema debe mantener una tasa de error inferior al 1% en operaciones estándar.
Tiempo medio entre fallos (MTBF) estimado en más de 30 días en entorno local.
Tolerancia a errores: validación de entradas, manejo de excepciones y mensajes claros ante fallos.
Registro de incidentes técnicos en la bitácora para análisis posterior.
Recuperación segura ante errores de exportación o movimientos inválidos.

Disponibilidad
El sistema debe estar disponible el 99% del tiempo durante el horario operativo institucional.
Acceso garantizado desde terminales conectadas a la red local mediante IP fija.
Reinicio automático del servidor en caso de interrupción no planificada.
Módulo de exportación y consulta debe estar disponible en todo momento para el administrador.
Mantenibilidad
El mantenimiento debe ser realizado por el equipo de desarrollo técnico.
Tareas de mantenimiento incluyen:
Actualización de dependencias (Composer, NPM).
Revisión de rutas y controladores.
Generación de estadísticas semanales y mensuales.
Limpieza de bitácora y respaldo de base de datos.
El sistema debe permitir ajustes sin afectar la estructura principal gracias a su arquitectura modular.
Portabilidad
El sistema está diseñado para entorno local, pero puede migrarse a servidor institucional con ajustes mínimos.
Uso de Laravel, PHP, Composer y Node.js, tecnologías ampliamente portables.
El 90% del código es independiente del servidor físico, gracias al uso de rutas relativas y configuración por entorno.
Compatible con sistemas operativos Windows, Linux y macOS.
Exportación de reportes y compilación de frontend no dependen de plataforma específica.
Otros requisitos
Esta sección contempla requisitos adicionales que no se incluyen en las categorías anteriores, pero que son relevantes para el desarrollo, implementación y uso del sistema.
Requisitos legales e institucionales
El sistema debe cumplir con las normas de confidencialidad de datos médicos y administrativos establecidas por la UPTAG.
La información registrada no debe ser compartida con terceros ni almacenada fuera del entorno local sin autorización institucional.
Los reportes generados deben incluir identificación institucional (nombre del servicio, fecha, logo si aplica) para su validez documental.
El sistema debe permitir la auditoría interna mediante bitácora de actividades, en cumplimiento con los procesos de control universitario.
Requisitos culturales y operativos
La interfaz debe estar en idioma español, con terminología adaptada al contexto médico-administrativo de la UPTAG.
Los formularios deben respetar la estructura organizativa local, incluyendo categorías de insumos utilizadas por el personal médico.
El sistema debe operar sin conexión a internet, respetando las condiciones de infraestructura tecnológica de la institución.

A. Glosario de términos
Insumo médico: Material o producto utilizado en la atención médica (gasas, jeringas, medicamentos).
Stock mínimo: Cantidad mínima definida para cada producto, que al ser alcanzada genera una alerta.
Bitácora: Registro cronológico de acciones realizadas por los usuarios dentro del sistema.
Movimiento: Entrada (donación) o salida (uso) de insumos médicos.
